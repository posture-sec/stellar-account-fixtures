The contract / version 1

Two files per fixture. Neither one takes my word for it.

This page mirrors SCHEMA.md, which is the contract; the file beats the page wherever they disagree, and validate.py beats both. What the schema defines is a shape for data, not a judgement: it says what a fixture has to look like so that a claim inside it can be checked.

The twelve keys Synthetic rules

Layout

SCHEMA.md 1. A third file in a fixture directory is a validator problem.

what the tree looks like

fixtures/<fixture-id>/
  account.json      the account resource, verbatim from Horizon
  fixture.toml      the sidecar: what this is, where it came from, what shape it has
corpus/
  root-<network>.json  the Horizon root document captured alongside the fixture
tools/
  capture.py        writes a new captured fixture and its root document
validate.py         checks the whole tree against this schema
test_validate.py    the tests for both
tests/
  test_roadmap_gate.py  the two roadmap gate scripts, run as subprocesses

A fixture id is kebab-case, matches ^[a-z0-9]+(-[a-z0-9]+)*$, and equals its directory name. Ids are part of the contract and are never reused: a fixture that leaves the tree takes its id with it. A directory holding anything beside those two files reports unexpected file(s), and one missing either reports missing file(s), because the schema does not know what a third file is for.

account.json

SCHEMA.md 2. The byte rules, and the three consequences of them.

The bytes are what Horizon returned for GET /accounts/<account-id>, re-serialised with json.dumps(payload, indent=2, sort_keys=True) plus a trailing newline. Nothing is stripped and nothing is added: an account resource is public ledger state, and a fixture that has been edited is a fixture whose provenance claim is a lie. LF line endings only, and a file that does not end with a newline is reported.

Fields follow Horizon
Which means they can change when Horizon changes. A re-capture with --update is how a fixture is refreshed, and the ledger number in the sidecar is what tells you how old the bytes are.
The read is point-in-time
An account that was multisig at ledger 65266865 can be single-signer tomorrow. last_modified_ledger is not decoration: it is the date on the claim.
Empty is a fact
data is present in some captures and empty in others. Empty means the account has no data entries, not that somebody dropped the field.

fixture.toml

SCHEMA.md 3. Flat TOML, one section, no tables. Unknown keys are refused.

Twelve keys, and the two columns that matter are the middle pair: five of them are provenance, and a fixture that was authored rather than read cannot have them. validate.py reports unknown key(s) in sidecar: ... for anything the schema does not define, on the reasoning that a key nobody defines is a key nobody reads.

The key table, as SCHEMA.md 3 states it
Key Captured Synthetic Meaning
schema_version required required Integer. This corpus is 1; see versioning.
id required required Kebab-case, equal to the directory name.
kind required required captured or synthetic.
scenario required required One sentence on what the shape is for, in plain words.
account_id required required G... ed25519 account id, checksum included.
network required required public or testnet.
shape required required Sorted list of the labels in section 5.
source_url required forbidden The exact URL that was read.
captured_at required forbidden YYYY-MM-DDTHH:MM:SSZ, UTC, not in the future.
ledger required forbidden last_modified_ledger of the resource, positive.
horizon_version required forbidden Version string from the endpoint that served it.
sha256 required forbidden SHA-256 of account.json as it sits on disk.

One row is worth more attention than the rest. shape is the only field in the sidecar checked against content rather than form: the validator re-derives the same labels from account.json and reports declared shape 'x' is not what account.json shows for a label the bytes do not support.

The synthetic kind

Allowed for a shape a search could not find, and stripped of every claim it cannot make.

What it may say

The seven keys every fixture carries. Its account_id still has to be a valid G... strkey with a checksum that verifies, so a consumer's tests can treat both kinds exactly the same way.

Its scenario must start with synthetic:.

What it may not say

Any of the five provenance keys. A fixture that was never read from anywhere has no URL, no capture second, no ledger, no Horizon version and no digest to record, and carrying one of them would be the specific lie this schema exists to refuse.

Reported as synthetic fixture carries provenance it cannot have: ....

Shipped today: none

All nine fixtures in the corpus are captures. The synthetic branch exists so a rare shape is not unreachable, and D-01 in the roadmap says a shape is fabricated only after the search for a real account failed. Two Phase 2 tasks permit something other than a capture in their Done when: 2.2 allows a synthetic fixture with the reason recorded, and 2.4 allows a written decision that the shape stays uncovered and why. 2.2 found a real account on the first pass that mattered, and 2.4 stays open rather than closed with a fabrication.

What an account id has to satisfy

SCHEMA.md 4. Checked by checksum, not by shape.

Only G...: an ed25519 public key, version byte 48, 56 base32 characters decoding to one version byte, 32 bytes of key material and a CRC16-XMODEM checksum over the first 33 bytes, appended little-endian. M..., C..., T... and X... are not account resources, and tools/capture.py refuses them before it makes a request. The checksum is what stops a typo or an invented address entering the corpus: validate.py recomputes it, and one flipped character returns nothing.

Seed strings are refused at three points

The capture tool will not write a response body containing a seed-shaped string. The validator scans both files of every fixture for one. And the test suite builds its seed-shaped samples from thirty-two zero bytes at run time, so a real key cannot appear in this repository by accident. A decodable seed and a shape-only fake produce distinct problem lines, the first saying “and its checksum verifies” and the second not.

Root documents

SCHEMA.md 6. Why a fixture cannot quietly be from somewhere else.

Every network used by any fixture
Network Passphrase that must appear in the root document Captures
public Public Global Stellar Network ; September 2015 eight
testnet Test SDF Network ; September 2015 one

corpus/root-<network>.json is the document the endpoint served at GET / while the capture ran, and a missing one reports missing; every network used must have its root document. mainnet and public are the same network with different names in different tools; this corpus says public because that is what Horizon and the passphrase both say. The name is the one a reader can check against a root document.

Versioning

SCHEMA.md 7. What makes this version 2 rather than a new key.

Still version 1
A key is added by adding it to SCHEMA.md, making validate.py accept it, and shipping fixtures that use it. Nothing is a version 2 candidate today.
Version 2
A key renamed, a shape label that changes meaning, or account.json stopping being verbatim bytes. The validator then has to read both for a release cycle so consumers are not broken mid-flight.
No tag either
D-04 keeps the corpus untagged until a consumer pins a version: a tag on a nine-fixture corpus invites the reading that the shape set is stable, and it is not. Pin a fixture by its sha256 instead, which is described here.

What the schema does not do

SCHEMA.md 8, and the reason the corpus stays small enough to read.

It does not say whether an account is well configured. It holds no expectations, no severities, no rule ids and no policy: those belong to Gauge, which reads a real account and evaluates rules, and to Airlock, which reads repositories. A fixture here is an input, and the only claim it makes is that these bytes came from that URL on that date at that ledger, or that a human wrote them and said so.

Two limits follow from the same choice. One account resource per fixture, so no transactions, offers, effects or operations in version 1 (D-05). And no re-read of the chain after a capture lands, except the one account the sibling action watches weekly, which is described on the consumers page.

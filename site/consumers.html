Consumer contract / roadmap Phase 3

Point a test at a directory. Pin it by digest.

There is no package here and no tag to depend on. A fixture is two files in a directory, and the useful thing about that is a consumer can check the claim instead of trusting it: recompute the digest, compare the declared shape with the bytes, and the corpus either agrees or your test says so.

Taking one

Two ways, and the difference is who sees a re-capture.

read a fixture from a checkout beside yours

import json
from pathlib import Path

fixture = Path("stellar-account-fixtures/fixtures/multisig-custody/account.json")
account = json.loads(fixture.read_text())

vendor one and prove it is still the capture

import hashlib, json, tomllib
from pathlib import Path

local = Path("testdata/multisig-custody")           # you copied two files
digest = hashlib.sha256((local / "account.json").read_bytes()).hexdigest()
sidecar = tomllib.loads((local / "fixture.toml").read_text(encoding="utf-8"))

assert digest == sidecar["sha256"], "the vendored bytes are not the capture the sidecar describes"
account = json.loads((local / "account.json").read_text())
assert set(sidecar["shape"]) <= shapes_of(account)   # your own re-derivation, or the tool's

The assert is the point. A vendored copy keeps the provenance in the same directory, so the test that reads it can check it, and a fixture whose bytes were edited afterwards fails loudly instead of passing against a shape nobody re-derived. Ids are part of the contract and are never reused or renamed; if a fixture has to go, SCHEMA.md 7 is the discussion.

Selecting by shape

The sidecar's shape list exists so a test does not re-parse Horizon.

every fixture with these labels

import tomllib
from pathlib import Path

CORPUS = Path("stellar-account-fixtures/fixtures")
WANT = {"multi_signer", "thresholds_nonzero"}

for sidecar in sorted(CORPUS.glob("*/fixture.toml")):
    data = tomllib.loads(sidecar.read_text(encoding="utf-8"))
    if WANT <= set(data["shape"]):
        print(sidecar.parent.name, data["account_id"], data["ledger"])

Select with <= against the set, not equality: a fixture that is multi_signer is also master_is_signer and not_sponsored, and a test that demands the whole label set will find nothing when a capture is refreshed and one field moves.

Pinning

A commit pin freezes files. A digest pin freezes facts.

Each captured fixture carries sha256 over the exact bytes beside it, so a consumer can record the eight characters it depends on and notice the day they stop matching. That is the difference between a test that breaks when somebody re-captures an account and a test that tells you the account changed and the ledger it changed at.

What is not settled

There is no machine-readable manifest of those digests yet. Roadmap 3.1 asks for tools/manifest.py to print one JSON line per fixture with id, account id, network, ledger and digest, and it is open, tracked as issue #17. Until it lands, pinning means reading twelve sidecars or copying a table.

D-03 is open too, and it decides 3.2: how a consumer takes the corpus at all. The three options and what each costs, in the roadmap's own words: a submodule breaks a contributor who has never used one, vendoring duplicates the bytes, and a download needs somewhere to host them. Nothing in Gauge's testdata/ came from here, and that is the honest state of Phase 3.

The one account read back from the chain

Roadmap 3.4, done on a runner rather than at a desk.

.posture/gauge.toml declares the account behind fixtures/testnet-multisig exactly as the sidecar captured it: six signers, the master key at weight 0, thresholds 3/3/3, every flag off, no home domain. .github/workflows/posture-watch.yml reads that declaration back from live testnet on Wednesday 06:41 UTC by pinning the sibling action stellar-posture-watch at deaf7dcc and asking it to build Gauge at da656733.

What a finding means

The tracking issue is #29, labelled fixture-drift, opened by the second run at ledger 5568533 with no findings. A finding on it says the capture no longer describes the live account: re-capture with --update and say which ledger it replaced, or explain on the issue why the capture stays as it is.

The third run found the issue by its state marker and printed issue #29 needs no change, left alone.

What it cannot see

The Gauge commit that action builds has no signer rule and no threshold rule, so the drifts this read can report are a flag appearing, a home domain appearing, or the account ceasing to exist. A seventh signer added to a testnet account is invisible to it, and the other eight fixtures are mainnet and outside the policy.

This is not gate G5: a watch consumes none of the files in this repository.

The workflow triggers on schedule and workflow_dispatch only, never on a pull request, because its token can write issues in this repository and nothing else. A dry_run input, defaulting off, lets a policy edit be checked before it files anything.

Giving a fixture back

The corpus grows by search, not by request, but a request is how a search starts.

If a rule you are writing needs a shape that the gap list says is uncovered, file it with the fixture request template and name the account id and the network if you know one: that is the whole difference between a search that ended and a wish. A capture needs a real account, so the accepted answer to most requests is a ledger number and a URL, or a written decision that the shape stays uncovered and why.

Two rules shape what a contribution can be. A fixture is written by tools/capture.py and never by hand (the refusals are in the open), and the corpus holds public ledger state only: no secret seed, in any file, ever. CONTRIBUTING.md is the pull-request contract, and every change moves ROADMAP.md in the same branch as the code.

Pre-release corpus, Apache License 2.0. The account data is public ledger state: what is licensed here is the compilation, the sidecars and the tooling. Nothing on this page calls an account well configured; the corpus holds inputs, and judging them belongs to the tools that read them.

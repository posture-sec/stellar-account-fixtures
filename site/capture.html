tools/capture.py / exit 0, 1 or 2

One tool writes a fixture. Twelve refusals before the disk.

A fixture that was edited rather than read is a fixture whose provenance claim is a lie, so nothing enters this corpus by hand. The tool computes the digest over the exact bytes it writes, labels the capture with the same function the validator uses, and refuses an input it can see is wrong before it spends a request on it.

The refusals What it does, in order

The invocation

Four required arguments, one account per run.

capture one account

python3 tools/capture.py --network public --account G... \
  --id my-new-shape --scenario "one sentence on why this shape is missing"
python3 validate.py
Flags, as the parser defines them
Flag Required What it does
--network yes One of public or testnet. There is no default, because an implicit network is the mistake this whole repository is built around: a G address is valid on both.
--account yes The account id, matched against ^G[A-Z2-7]{55}$ and then against its own checksum.
--id yes The fixture id: kebab-case, becomes the directory name, and is part of the contract once shipped.
--scenario yes One sentence on why the shape is worth having. This is prose the validator cannot check, so keep counts out of it; roadmap 0.6 is the open task deciding what to do about that.
--root no Corpus directory, default .. The tests point it at a temporary directory, which is how a capture path is exercised without writing into the corpus.
--update no Replace a fixture that already exists. Without it an existing directory is refused. See what a re-capture means.

What it does, in order

Two requests, one pair of files, one root document rewritten.

1. Refuse locally
Before any request: the fixture id is kebab-case, the account is G... by shape, the checksum of that account verifies, the network is known, and the target directory either does not exist or was named with --update. A typo costs no round trip.
2. Verify the network
GET <endpoint>/, capped at 128000 bytes, parsed as JSON, and its network_passphrase compared with the passphrase that network carries. A mismatch is refused, which is the only thing standing between a capture and the reading that a mainnet account is a testnet one.
3. Read the version
From coreversion or horizon_version on that same root document, and unknown if neither is there; Horizon 30 stopped reporting coreversion on the root. All nine fixtures here record 30.0.0-b3ff4119cc99ebcc8048334f5ec64e78c16d1666.
4. Fetch the account
GET <endpoint>/accounts/<id>, capped at 512000 bytes, 15 second timeout, three attempts with 1.5s, 3.0s and 4.5s waits after each failure, through an opener that refuses a 3xx instead of following it. A read that never succeeds costs nine seconds and no file.
5. Refuse the body
If it contains a seed-shaped string, if it is not an object, or if the account_id inside it is not the one requested. The last of those is why a response cannot be renamed into a fixture for a different account.
6. Write the bytes
json.dumps(payload, indent=2, sort_keys=True) plus a newline, and the SHA-256 computed over exactly those bytes. Pretty-printing changes the digest from whatever Horizon happened to emit, which is why the digest is of the file and not of the wire.
7. Write the sidecar
kind = "captured", the URL, the UTC second, last_modified_ledger, the version string, the digest, and shape labelled by shapes_of() imported from the validator. One definition of a label, so a capture cannot invent one nothing checks.
8. Rewrite the root document
A second GET / replaces corpus/root-<network>.json. This is why that file moved when 2.1 and 2.2 landed: its ledger counters changed while the passphrase did not. It is also why two captures cannot run at once against one checkout.

Every refusal, in its words

Exit 2 is a refusal, 1 is a failed fetch, 0 wrote a fixture.

A refusal prints capture refused: and exits 2; a failed fetch prints capture failed: and exits 1
Message Code What it is stopping
fixture id 'My_Shape' is not kebab-case 2 A directory name that would not survive the id rule in SCHEMA.md 1.
account 'M...' is not a G... ed25519 account id; M... and C... addresses are not captured here 2 A muxed or contract address, which is not an account resource and has no GET /accounts/ read.
account 'G...' is G-shaped but its checksum does not verify; a typo is refused here rather than 404ing at Horizon 2 An invented address. This is the refusal that keeps a fabricated account out of a corpus other people write tests against.
unknown network 'futurenet'; expected one of ['public', 'testnet'] 2 A network with no endpoint and no passphrase to check.
fixtures/default-plain already exists; pass --update to replace it 2 Silently overwriting a capture somebody else pinned by digest.
https://horizon.stellar.org reports network_passphrase 'Test SDF Network ; September 2015', expected 'Public Global Stellar Network ; September 2015' 2 Bytes from the wrong network filed under the right name.
<endpoint>/ did not return a JSON root document: ... 2 An HTML error page or a captive portal, which would otherwise raise instead of refusing.
response from <url> exceeds the 512000 byte cap 2 A body large enough to be something other than one account.
<url> answered 302 with a redirect to <other>; the corpus does not follow redirects 2 Writing bytes served from somewhere else under the URL the sidecar records as its source. The Loopback cases in test_validate.py run this against a server the test starts itself.
captured body contains a seed-shaped string; refusing to write it 2 A key in the tree. This is a guard against a mistake, not a claim about Horizon: an account resource has no reason to carry one.
<url> returned list, expected an account object 2 A page envelope or an error array read as a resource.
response describes '<other-id>', not the requested '<id>' 2 A fixture whose sidecar would name an account its bytes do not describe.
<url> unreachable after 3 attempts: URLError 1 Nothing being written from a read that did not happen. No file, no sidecar, and the exit code says the endpoint was the problem.
<url> unreachable after 3 attempts: HTTPError 1 An account that does not exist, a 429 or a 5xx. urllib raises for those, so they arrive through the same path as a socket failure and burn all three attempts; the answered <status> branch below it only fires on a response that was not an exception.

Quoted from tools/capture.py and the messages it builds. FakeHorizon replaces one seam, capture.fetch, and records every URL it is asked for, so each local refusal is asserted together with the fact that the account was never requested; Loopback covers the two fetch behaviours a provenance claim depends on, an over-sized body and a redirect. A 404 is not among the tested paths: read from the code and confirmed against a loopback server, it comes back as the HTTPError row above.

Exit 0 is the only write

A run that prints wrote fixtures/<id> has replaced the directory's two files and the network's root document. Anything that exits 1 or 2 has written nothing, which is why pointing the tool at a real account is a decision you can take back: a refusal leaves the corpus exactly as it found it.

The checksum, and how its byte order was found

56 characters, 35 bytes, one comparison.

A strkey is base32 over ABCDEFGHIJKLMNOPQRSTUVWXYZ234567: 56 characters decoding to 35 bytes, a version byte, 32 bytes of key material, and a CRC16-XMODEM over the first 33 bytes appended little-endian. G is version byte 48, S is 144, and the same decoder tells them apart, which is how a shape-only seed and a decodable one get different messages.

The version that failed first

The first implementation of this check compared the checksum big-endian and marked all six real captures invalid. That is how the byte order was found: not by reading a specification, but by a validator refusing six accounts that Horizon had just served. Roadmap 0.2 records it, and test_encoder_and_decoder_are_inverses covers versions 48, 96 and 144 so the order cannot silently flip back.

What --update means

A re-capture is a new fact about the same account.

It is the only way a captured fixture changes after it is on disk. The bytes are replaced, the digest is recomputed, and ledger and captured_at move with them, so the sidecar describes the read that is now in the directory rather than the one that started it. The changelog row has to say which ledger it replaced.

What stays true

The fixture id, the directory name, the two files, and the claim that these bytes came from that URL. A consumer pinning the id still gets an account resource for the same address.

Nothing but the ledger moves the identity of a fixture.

What breaks

Anything that pinned the old sha256. That is the point of a digest pin rather than a commit pin, and it is why roadmap 3.1 asks for tools/manifest.py: a consumer that cannot see the digest list cannot see a re-capture coming.

D-04 keeps the corpus untagged, so there is no version that promises stability.

Two related refusals are the validator's rather than the tool's: an id reused by a second fixture reports id 'x' already used by ..., and a second capture of the same account reports account G... already captured as .... One account, one fixture.

What the tool does not do

The refusals it does not make, stated plainly.

  • It captures one account per run. There is no --all, no directory of ids, and no re-read of the corpus; refreshing eight fixtures is eight runs and one changelog row saying which ledgers moved.
  • It does not judge anything. No threshold is compared with a signer weight, no flag is called good or bad; that is Gauge's job and this corpus holds no opinions.
  • It does not install. D-02: validate.py and tools/capture.py import nothing outside the standard library, so a capture is python3 and a network, nothing else.
  • It does not write a synthetic fixture. That kind exists for shapes a search could not find, and it is authored by hand in a directory the tool will not touch, under the rules in the schema.
  • It does not prove the capture is still true. A sidecar is a claim about one ledger, and only the watched account is read back from the chain after it lands.
